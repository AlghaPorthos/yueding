# Backend Full Mission

## Outcome

交付一个可上线维护的合同阅读器后端：用户上传合同后，系统完成文档解析、质量评估、结构化条款抽取、非 LLM 法律条文检索与意图对齐，再按证据约束调用 LLM 生成解释、行动建议和协商草稿；所有结论都能回到合同原文、法律条文版本和处理链路。

## 产品边界

第一优先级是中国大陆个人用户的租房合同，之后通过规则包扩展到劳动、培训、装修、摄影等合同类型。法律检索器提供事实和对应条文，不替代律师，也不直接判定“违法/无效”。没有充分依据时返回 `not_found` 或 `needs_review`。

## 核心领域模型

- `User`、`Workspace`：用户、工作区、配额和权限边界。
- `Contract`、`ContractVersion`：合同身份、原文件哈希、版本、来源、状态和保留期限。
- `DocumentPage`、`TextSpan`：页码、段落、字符偏移、文本提取方式和质量分数。
- `Clause`、`ClauseEvidence`：合同条款、原文片段、条款类型、抽取来源和置信度。
- `LegalSource`、`LegalProvision`、`RulePack`：法律来源、条文版本、辖区/生效期和合同类型规则。
- `Alignment`：合同意图与法律条文的确定性匹配、匹配理由、算法版本和状态。
- `Finding`：对外返回的引用式结果，包含严重程度、后果、置信度和待核对事项。
- `Job`、`JobAttempt`、`Artifact`：异步任务、重试记录、取消状态和中间产物。
- `Reminder`、`ChecklistItem`、`DraftVersion`、`AuditEvent`：提醒、履约清单、协商草稿版本和审计事件。

## 分阶段路线

### Phase 0: MVP 闭环

完成 PDF/图片入口、页级文本、四类租房条款、行动卡片、引用核验和最小 API。3 份样本约 20 个标注点作为第一批回归集。

### Phase 1: 文档摄取与 OCR 质量

支持可检索 PDF、扫描 PDF 和图片；加入 MIME/大小/页数校验、去重、方向纠正、分辨率检查、文字覆盖率、OCR 置信度、表格/页眉页脚处理和人工复核标记。OCR 结果必须保存页码、字符区间、引擎版本和质量原因，低质量输入不得生成确定性结论。

验收：同一输入幂等；空页、损坏文件、低清图片、超长文件和 OCR 失败都有稳定状态；抽取结果可以回到页面坐标或文本范围。

### Phase 2: 非 LLM 法律快速检索与意图对齐

建立可版本化的法律语料库，只收录可追溯来源：法规名称、条文号、辖区、生效/失效日期、来源 URL、抓取时间和内容哈希。使用本地全文索引（FTS/BM25、短语匹配、同义词和正则规则）实现快速检索，不调用 LLM。

合同意图先经过条款类型、义务主体、动作、金额、期限、条件和例外的规则化归一，再与法律条文做确定性对齐。对齐记录必须包含命中的词/短语、规则 ID、法律版本、算法版本和 `matched | ambiguous | not_found` 状态。索引更新采用构建新版本后原子切换，保留旧版本可回放。

验收：相同输入返回稳定排序；能解释为什么命中；法律版本变化可重跑；没有条文依据时不生成法律结论。

### Phase 3: 引用式结果与证据契约

统一结果格式，建议字段如下：

```json
{
  "content": "合同中的具体内容或归一后的事实",
  "contract_evidence": [{"page": 3, "span_id": "p3-s12", "quote": "..."}],
  "legal_provisions": [{"source": "...", "article": "...", "version": "...", "quote": "..."}],
  "severity": "low|medium|high|unknown",
  "consequences": ["可观察的履约或争议后果"],
  "confidence": 0.0,
  "status": "confirmed|needs_review|not_found",
  "reasoning": {"rules": ["rule-id"], "retrieval": "bm25|phrase|none"},
  "generated_actions": [],
  "disclaimer": "不构成针对个案的法律意见"
}
```

程序必须校验页码、span、合同原文和法律条文版本；引用不存在、版本失配或置信度不足时降级为 `needs_review`。对外响应区分事实、法律对应、模型生成内容和用户待确认内容，避免把生成文本伪装成来源。

### Phase 4: 受证据约束的 LLM 链路

LLM 只消费已经通过程序校验的合同证据、法律候选和规则包，不负责自由检索法律。链路拆为：结构化抽取补全 -> 证据摘要 -> 严重程度/后果候选 -> 行动卡片 -> 确认消息/协商草稿。每一步使用独立 schema、超时、token 预算和输出校验；失败时保留确定性结果并标记生成失败。

合同原文和法律文本作为不可信数据输入，必须与系统指令隔离。禁止模型新增无法在证据集合中定位的引用；所有 LLM 输出都要经过 JSON/schema、引用存在性和敏感信息检查。

### Phase 5: 用户、合同和业务生命周期

加入注册/登录、工作区权限、合同列表、版本比较、删除/导出、审阅状态和幂等请求。支持补充约定版本、行动卡片状态、关键日期、入住/退租履约清单和提醒渠道。草稿必须有版本号、来源证据、作者、确认状态和回滚能力。

### Phase 6: 异步任务、持久化与可靠性

上传、解析、OCR、抽取、检索、LLM、导出都进入持久化任务表；任务支持 `queued/running/succeeded/failed/canceled`，幂等键、进度事件、超时、指数退避、最大尝试次数、死信和人工重试。中间产物可复用，取消不会留下“成功”结果，服务重启后能恢复未完成任务。

### Phase 7: 权限、隐私、审计和成本

建立用户/工作区/资源级授权，合同对象存储加密、传输加密、密钥轮换和下载授权；对身份证号、住址、电话、银行信息做识别、遮盖和日志脱敏。审计记录谁在何时查看、导出、删除或生成草稿。提供保留期限、硬删除、备份过期和用户数据导出。

模型供应商通过统一 provider 接口接入，按任务配置质量档位、token/费用预算、并发上限、超时和熔断；主供应商失败时只在允许的隐私策略下切换，记录 provider、模型、版本、token、耗时和费用估算，不记录密钥或完整合同原文。

### Phase 8: 生产部署与运维

提供配置校验、数据库迁移、对象存储、消息队列、worker、API、定时任务和反向代理的部署定义；健康检查区分存活/就绪，监控任务成功率、解析/OCR质量、检索延迟、LLM失败率、队列积压、费用、存储量和删除延迟。日志具备 request/job/contract 关联 ID，告警可定位到具体阶段。

### Phase 9: 回归、评估和发布门槛

维护脱敏样本集和人工标注集，分别评估 OCR 质量、条款召回、引用准确率、法律对齐准确率、严重程度一致性、LLM 格式通过率、端到端延迟和成本。每次规则包、法律语料、提示词、模型或解析器升级都记录版本并重跑回归；任何引用错误、敏感信息泄漏或任务数据丢失都阻断发布。

## 依赖顺序

Phase 0 -> Phase 1 -> Phase 2 -> Phase 3 -> Phase 4；Phase 5 和 Phase 6 在 Phase 1 稳定后并行；Phase 7、Phase 8 在有持久化和任务链路后进入；Phase 9 贯穿所有阶段。

## 完整体交付门槛

- 法律检索和意图对齐在无 LLM 模式下可独立运行并解释命中原因；
- 每条对外 Finding 都能定位合同原文，法律对应带来源和版本；
- LLM 只能在证据集合上生成，输出失败不破坏确定性结果；
- 用户、版本、任务、草稿、提醒和审计数据可持久化、恢复、删除和追溯；
- 主/备用模型、费用预算、重试和熔断可观测；
- 脱敏回归集通过后才能部署生产。

## Non-goals

系统不提供律师代理、不自动代表用户签约或谈判、不保证个案法律结论，不把公开法律检索结果当作对具体事实的最终裁判。
